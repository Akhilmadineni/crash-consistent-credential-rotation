# A5P5 - Crash-consistent credential rotation

**Track:** Track 6  
**Application:** Key and credential rotation for blockchain nodes and clients

> This dataset is synthetic, generated by gen_author5.py with seed 2081. It must be described as synthetic in any publication.

## Simulated scenario

Credentials for blockchain infrastructure (validator signing keys, RPC TLS certs, node DB passwords, API tokens, P2P keys, HSM wrapping keys) are rotated by an orchestrator that touches the secret store, the target system and many clients. Fault injection crashes the orchestrator at different steps. Each row is a rotation run with protocol, crash point, caching/grace parameters and recovery mode; ground truth is whether the system ended in an inconsistent state and the impact.

## How it was generated

- Step order x crash point: each protocol runs the rotation steps in a different order (naive: create -> overwrite store -> node/DB -> clients; 2PC: create -> stage pending -> node/DB -> commit -> clients -> revoke; dual overlap: create -> add to node/DB (both valid) -> store -> clients -> revoke old; versioned lease: create -> publish version -> node/DB -> clients renew lease -> retire), so risk comes from a protocol x crash-point table (e.g. naive is worst after the store overwrite, 2PC after the node/DB switch before commit, versioned lease during client reload).
- Conjunction: journal replay sharply reduces risk only when a write-ahead journal exists; replay without a journal is useless.
- Interaction: manual recovery is mainly harmful when the old-credential grace window is < 300 s (it expires before the operator acts).
- Regime: restart-from-scratch after the node/DB already switched (2PC / dual overlap) mints another credential and orphans state.
- Conjunction: in the dual-overlap protocol a crash before revoking the old credential is only unsafe when client cache TTL exceeds the grace window.
- Regime: validator keys crashing between node switch and client reload without journal replay carry double-signing risk.
- Threshold: secret-store replication lag matters only above ~5 s and only for crash points that read replicas; without a crash, only > 50-client fleets on > 5 s lag split.
- Latent sub-population: ~4% of rotations have clients with pinned/hard-coded credentials and end inconsistent far more often.
- Linear part kept: log client count, hot reload, public L2 bridge, validator keys, log replication lag; plus N(0,0.55) unmodelled variation; P(inconsistent) = sigmoid(2.8 z) calibrated to ~33%.
- final_state category is determined by crash point / credential type for inconsistent runs.
- auth_failure_minutes ~ LogNormal growing with client count, manual recovery and cache TTL; failed transactions = minutes x tx rate x U(1%,8%); missed blocks ~ Poisson for validator keys.
- Noise: 5% Gaussian, ~0.7% outliers (replication lag, tx rate), 1-3% missing (replication lag, tx rate, cache TTL).

## Target / label columns

- `inconsistent_state` (binary, ~33%).
- `final_state` (multi-class).
- `auth_failure_minutes`, `failed_transactions`, `missed_blocks` (impact regression).

## Suggested experiments

1. Inconsistency prediction: classify inconsistent_state (F1, PR-AUC); compare a logistic model with a non-linear model able to capture protocol x crash-point (step-order) interactions.
2. Protocol comparison: inconsistency rate and mean auth_failure_minutes per rotation_protocol x injected_crash_point (counterfactual table).
3. Impact regression on log auth_failure_minutes (R2) and validator missed blocks.
4. Policy search: choose grace period / cache TTL / journal settings minimising expected failed transactions under a rotation-time budget.

## Notes

- Realism noise: ~5% Gaussian measurement noise on numeric signals, 1-3% missing values in a few columns, ~0.5-1% gross outliers in a few columns. Label/target columns are never noised by the measurement-noise step (they carry their own stochasticity).
- All IDs, sites, regions and assets are synthetic; no real people, companies, IPs or CVEs.
- The dataset contains inputs and ground truth only - no results of any proposed method.
